## 1. Executive Summary

Foreman at `7770ec3` is a large, unusually well-engineered piece of Windows systems software with a genuine security architecture behind it, and it is also a codebase where the round-2 lesson repeated itself in every single P0 fix. Not one of the five P0 remediations comes back clean. Three of them (`P0-1`, `P0-3`, `P0-5`) closed the exact path the audit named and left a reachable sibling open. Two of them (`P0-3`, `P0-4`) introduced new failure modes that are worse than the bug they replaced, and the `P0-1` fix turned a benign Guardian boot race into a destructive settings wipe. The good news is real and specific: the payment card vault's cryptographic core and per-entry ACL are correctly built, an ordinary per-harness agent genuinely cannot reach a PAN or CVV in plaintext through any path I could trace, `AdbBridge` remains the best-defended code in the repo, and `866af36`'s install rollback, `ElevatedSidecarController`'s 60s connect timeout, and `EventLogStore`'s crash-repair logic are all correct work that survived adversarial refutation.

The five things that matter most:

1. **The settings seal has three independent critical-class holes.** Deleting `settings.json` outright is silent and disarms the presence lock and decoy auditing on every launch (`SettingsStore.cs:62`). Any future change to `SecurityProjection` wipes every upgrading user's settings and fires a false tamper alarm (`SettingsSeal.cs:43-88`, no version field, and it demonstrably changed between `v0.1.0-alpha2` and `alpha3`). A Guardian that is merely slow to start now quarantines `settings.json` and resets the entire posture to defaults (`SettingsSeal.cs:125` + `SettingsStore.cs:96-116`), a regression `866af36` created.
2. **The Guardian install trust anchor is still bypassable, three audits running.** `GuardianIntegrity.cs:79` skips the recorded-root check entirely when nothing is recorded, which is the state of every machine that has not already completed a Guardian install, and `--allow-unsigned-development` is read from `argv` on the binary the attacker invokes (`Program.cs:30`). The new HKLM anchor also doubles as a permanent lockout primitive against the genuine Foreman.
3. **The release payload validator has no purity check on the payload root.** This was demonstrated empirically, not inferred: a real 591 MB alpha4 payload with a planted root `version.dll`, a new `amd64\KernelTraceControl.dll` subdirectory, a hidden root file and an extra file inside a shipped extension passes the unmodified `scripts/Test-ReleasePayload.ps1` with exit 0, then gets signed, checksummed and Sigstore-attested. `915fdd3` hardened the four helper directories round 2 named and left the directory containing `Foreman.exe` unchecked.
4. **The payment card feature is safe at the store and weak at the gates.** Three of the four "stricter gates" `docs/vault-design.md:78-84` advertises have a reachable sibling path, and the sole documented consent boundary on a card release still shows the same six generic words the operator taps through to unlock their own vault.
5. **The decoy tripwire, the product's flagship detection, is permanently disarmed by an ordinary `File.Delete`, generates no audit record, and the Setup Health checklist then reports it green twice.**

**Shippable/judgeable verdict.** As a Build Week submission this is judgeable now and the engineering depth is not in question. The subsystem architecture, the invariant discipline, the volume of correct low-level work (WMI PID-reuse safety, ETW sidecar handshake, ADB argument-vector hardening, AEAD envelope AAD binding, SHA-pinned CI actions) is well above what a hackathon normally produces. As a security product for public distribution it is not ready. The specific blockers are the supply-chain payload gap (a planted binary survives signing and attestation) and the Guardian unsigned-install anchor (one self-consented UAC prompt persists an attacker binary as the sole authorized SYSTEM caller). Both are P0 in the action plan.

6. `mcp-surface` (43 tools, `ForemanMcpTools.cs`, `ForemanState.cs`, `McpServerHost.cs`, `CallerScope.cs`, `McpAuthToken.cs`, `LiveWeaveBroker.cs`)
7. `computer-use-android` (`CuBroker`, `CuHeuristics`, `AuditPipeline`, `AdbBridge`, Desktop CU, `CuPilot`, `CuSidecar`)
8. `detection-monitor` (heuristics, pattern library, `AgentConfigScanner`, `SecretRedactor`, `Foreman.Monitor`)
9. `app-ui-qol` (composition root, `TrayController`, `DashboardWindow` and its 11 hosted tabs)
10. `release-installer-ci` (`.github/workflows/`, `scripts/`, `installer/foreman.iss`, `CODE_SIGNING.md`, `docs/release-checklist.md`)

Six adversary personas were run against those maps. Three produced attack chains that survived refutation and appear in this report as their own findings: `same-user-local` (a medium-integrity implant running as the logged-in user, never touching MCP), `operator-human-factors` (defeating consent rather than code), and `supply-chain` (one write into the build tree). The other three folded into subsystem findings or were refuted.

Five round-2 P0 remediations were verified by tracing every reachable path in the current code, not by reading the new tests.

### What was thin or not covered

- **No dynamic execution of privileged paths.** This was a read-only audit. The elevated Guardian install was never run, the SACL sidecar was never armed, and no live MCP session was driven. Two findings are therefore marked *likely* rather than *confirmed* (`%ProgramData%\Foreman\guardian` junction pre-plant, pipe-name squat) even though the code-level premises are verified.
- **The one exception is the release payload**, which was tested empirically against a real 591 MB alpha4 payload mirrored into scratch. That finding is demonstrated, not inferred.
- **`Foreman.Platform.Linux` (7 tests) got a shallow pass only.** It is not on the Windows attack surface and was not a focus.
- **The Chrome extensions were read only where they intersect the card fill path (`extension/background.js:226-345`, `:401-525`) and the release payload.** LiveWeave's DOM model and editor surface were covered by the separate `docs/` LiveWeave review and are not re-derived here.
- **No fuzzing, no load testing, no timing analysis.** Performance findings are limited to specific hot paths read statically (`BoundedEventHistory.Add`, `CredentialSweepAggregator`, the dashboard-open dispatcher block).

### Verification bar

Every candidate finding was put through adversarial refutation by independent readers instructed to kill it: verify the cited lines exist and say what is claimed, check whether it is reachable, check whether it is mitigated elsewhere, and check whether project docs declare it an accepted scope limit. Critical and high findings required two independent confirmations; where a finding carries a 1/2 split the dissent is summarised inline so the maintainer can weigh it. Two findings did not survive and appear in section 8 with the reasoning that killed them. Findings that duplicated across subsystem maps (the card verb-scoping bypass appears in three maps, the guardian-unreachable wipe in two) were merged.

The standing rule from round 2 was applied throughout: a green test proves the path the test exercises and nothing else. Every "fixed" claim in this report was traced in source, and where a new test exists that appears to cover a finding, the test's actual coverage is stated.

## 3. Payment Card Vault (first coverage)

`40d2ff1` adds payment cards as a new sealed vault entry kind (PAN, cardholder name, expiry month/year, security code, billing address), reachable only through selected `{{vault:origin/entryId/field}}` references, resolvable only by the browser-extension executor at the fill boundary. This is the most sensitive thing the product has ever handled, so the core question deserves a direct answer.

### Can an agent reach a PAN or security code in plaintext?

**An ordinary per-harness AI agent: no.** I could not find any path. The reasons are structural, not accidental, and they are worth naming because they represent correct work:

- `CuResolveVault` refuses every caller that is not the operator or `browser-extension` (`ForemanMcpTools.cs:1687`).
- The value never enters `cu_action_status`, `cu_complete_action`, or the event log. The vault release line logs the reference only (`ForemanMcpTools.cs:1739`).
- The extension's own result payload zeroes the field (`extension/background.js:487` sets `value = ''`, returned at `:490`).
- The summary DTO exposes only `CardLastFour` and `HasCardSecurityCode` (`AeadVaultStore.cs:80,84`), and there is no vault-listing MCP tool at all.
- The per-entry ACL genuinely isolates two cards sharing one origin (`VaultResolver.cs:28` plus the `EntryId` match inside `FindEntryLocked`, `AeadVaultStore.cs:240`).
- A two-segment legacy reference cannot reach a card: the no-`entryId` lookup is Login-only (`AeadVaultStore.cs:243`) and every card field is guarded by `when e.Kind == PaymentCard` (`AeadVaultStore.cs:101-106`), so both fail closed.

**A same-user process that mints a `browser-extension` token: yes, subject to one presence tap, and that tap is generic.** The codebase concedes this actor explicitly (`ForemanMcpTools.cs:1683-1686`, `docs/vault-design.md:97-101`): the executor identity is not a same-user boundary, and the presence tap *is* the boundary. That is a defensible design. The problem is that the tap does not carry the information a human needs to exercise it.

### What is genuinely solid

The crypto and the store came out clean, and `40d2ff1` did not weaken a single existing invariant:

- Fresh random salt and nonce per write, double-bound header AAD, untouched (`VaultCrypto.cs:44-53,83-84`).
- Cards live inside the same sealed document (`VaultDocument.cs:49`), so they ride the identical envelope with no new key, file or nonce discipline.
- Existing vaults migrate cleanly (new properties default).
- The entry-ID design is well built: a bare two-segment reference resolves Login entries only (`AeadVaultStore.cs:240-245`), so a card can neither be hijacked by a legacy `{{vault:host/password}}` reference nor reached without its 48-bit id.
- Luhn and expiry validation are duplicated in the store (`AeadVaultStore.cs:257-273`) rather than trusted from the UI, and digits-only normalisation is real.
- `UpdateItem`'s blank-keeps merge was correctly extended to the PAN and CVC (`AeadVaultStore.cs:171-182`).
- `DepositCrypto`'s per-deposit ephemeral key and SPKI-hash AAD (`DepositCrypto.cs:27-33,92-94`) plus sealed-vs-clear pubkey swap detection (`VaultService.cs:261-274`) are thoughtful work that cards inherit for free.

### What is exposed

`docs/vault-design.md:78-84` advertises four stricter gates for cards. Three of the four have a reachable sibling path.

**Gate 1: "every card-bearing CU action is a final Hold requiring explicit operator approval" (`vault-design.md:79`). BROKEN, confirmed.**
The check lives inside a `verb == "type"` branch: `CuHeuristics.cs:31` opens `if (string.Equals(a.Verb, "type", ...))` and the card scan sits at `:35-38`. Browser actions have no verb allowlist at the broker (`CuBroker.cs:106` and `:115` gate Desktop and Android only), `ForemanMcpTools.cs:1521-1522` checks only that the verb is non-blank, and `CuResolveVault` checks modality but never the verb (`ForemanMcpTools.cs:1698`). Submit `cu_submit("browser","click",{"selector":"#ok","note":"{{vault:shop.example/personal01/cardnumber}}"})`: `CuHeuristics` returns null, `FastPathAuditor.Project` (`FastPathAuditor.cs:47-49`) does not even project the `note` key, the verdict is `Allow` at confidence 1.0, the item reaches `Executing`, and `cu_resolve_vault` releases the card with no operator Hold. The comment at `CuHeuristics.cs:33-34` asserts the invariant ("never let it ride an automatic allow path") that a one-word verb change defeats. The test shipped with the feature, `AuditorTests.FastPath_PaymentCardReference_HoldsAndIsFinal_EvenInTextField`, calls `TypeInto(...)`, so the sibling stayed green. This is round 2's pattern verbatim.

**Gate 2: "a payment-card reference must be the entire field value, never embedded in other text" (`vault-design.md:80`). BROKEN, confirmed.**
`ForemanMcpTools.cs:1707-1709` validates whole-value against `item.Action.Args.Values.Any(...)`, so a match in a *different* arg satisfies the check for the arg actually being filled. Submit `{"value":"note {{vault:shop.example/personal01/cardnumber}} end", "x":"{{vault:shop.example/personal01/cardnumber}}"}`: the guard passes on `x` while the extension resolves and fills from `value`, typing the PAN surrounded by agent-chosen text. The signup check at `:1713-1715` has the identical shape (pre-existing). The added test `CuResolveVault_EmbeddedPaymentCardToken_RefusedBeforeResolver` builds a single-arg action and cannot see this.

**Gate 3: "the target field must carry a payment `autocomplete` attribute, and exactly one card field per action" (`vault-design.md:80-83`). BROKEN when a password reference rides along, confirmed.**
`extension/background.js:295-299` is `if (p.requirePasswordField) { ... } else if (p.requiredAutocomplete) {` (same chain in `injFill` at `:334-338`). `needsPasswordField` (`:226`) returns true for a password or signup ref, so the `else if`, which holds both the `__invalid__` "exactly one card field" guard and the `cc-*` target check, never runs. With refs `[password, cardnumber]`, `paymentAutocomplete` correctly computes `'__invalid__'` (`:240`) but that verdict is unreachable, and the fill proceeds against any `input[type=password]`. A PAN gets typed into a password field on the merchant page. Two of the four gates defeated in one action.

**Gate 4: the presence tap. INTACT AS CODE, DEFEATED AS CONSENT.** See the critical finding in section 5. The dialog reads "Authorize a Foreman security change" (`PresenceGate.cs:125`) because `PromptReason` has no case for `ResolveVaultCredential`. The origin-bearing text the App builds (`App.xaml.cs:551`) reaches only the cache key and the log. On the FIDO2 path it is worse: `WebAuthnPresenceVerifier.cs:47-66` accepts `reason` and never uses it, so a security-key operator releases a PAN and CVC on a prompt with no descriptive text at all.

### Other card-specific findings

**Granting a model access to a card requires no presence tap (high, confirmed).** `VaultView.xaml.cs:374` writes the harness list straight through `Upsert`/`UpdateItem` in `SaveCardClick` (`:385-392`) with no `PresenceGuard` call. The same codebase demands `forcePresence: true, freshTap: true` to enroll the ADB bridge (`SettingsView.xaml.cs:345-348`). Granting an agent phone-tap authority needs a fresh hardware tap. Granting it the operator's card number does not.

**An "operator only" card, the default state of every new card, can never be resolved by anything (medium, confirmed).** `ForemanMcpTools.cs:1534` stamps the literal string `"operator"` into `ByHarness`, but `App.xaml.cs:553` computes `isOperator: string.IsNullOrEmpty(byHarness)`, which is never true on this path. `VaultResolver.cs:28` then falls to `info.AllowsHarness("operator")`, and no connector has that id. The card form opens with every model switch off, the list row renders `Acl = "operator only"` (`VaultView.xaml.cs:499`) next to a copyable reference hint (`:500-502`), and the empty-connector hint promises "cards remain operator-only" (`VaultView.xaml`, `NoCardHarnessesHint`). All three advertise a mode that always fails with "this harness is not authorized for that credential". The resolver's operator branch is dead on the whole `cu_resolve_vault` path, so this predates cards and affects logins too, but for cards there is no workaround at all: the card ACL switches are built only from configured harness connectors (`App.xaml.cs:504-512`).

**Saving a card silently deletes any vault item sharing its nickname (medium, confirmed).** `VaultView.xaml.cs:392` calls `_vault.Upsert(entry)`, reaching `AeadVaultStore.cs:120` `_doc!.Items.RemoveAll(i => string.Equals(i.Name, entry.Name, OrdinalIgnoreCase))`. Name a card "store.example" when a login of that name exists and the login's password and TOTP seed are gone with no prompt. The agent-facing write path was deliberately given a no-clobber variant for exactly this reason (`TryAddNew`, `AeadVaultStore.cs:132-148`); the operator UI does not use it.

**The security code is stored indefinitely, released through the identical path as any other field, and cannot be cleared (medium, confirmed).** Stored as a plain property (`VaultDocument.cs:31`), returned by the same switch as everything else (`AeadVaultStore.cs:105`). Blank-keeps on edit (`AeadVaultStore.cs:179-180`, `VaultView.xaml.cs:381`) means the only way to remove a stored CVC is to delete and re-create the card. Foreman is not a merchant so PCI-DSS does not bind, but nothing in the code or `docs/vault-design.md:64-84` shows this was a deliberate choice: the CVC gets no distinct gate, no distinct audit line, no distinct verdict text, and no lifetime.

**`SecretRedactor` recognises no card-number shape (high, confirmed).** `SecretRedactor.cs:29-61` is the complete rule table: Authorization headers, URL userinfo, `--password` flags, JWT, `gh*_`, `xox*`, `sk-`, `AKIA`, Stripe, PEM. No PAN rule, and neither the flag list at `:38` nor the KEY=value list at `:41` contains `card`, `cvv`, `cvc` or `pan`. Three egress paths depend on it: the durable JSONL (`EventLogStore.cs:100`), the Windows Event Log (`OsEventLogForwarder.cs:35`, forwards Severity >= High), and `CloudDeepJudge.cs:39`, which ships `text`/`url` off the machine to a third-party model under the assertion at `CloudDeepJudge.cs:13-14` that "the action is SECRET-REDACTED before any of it leaves the machine". The vault's own release line is fine (it logs the reference), but the product now invites the operator to keep card data in a process that writes a durable log. The codebase already has Luhn twice (`AeadVaultStore.cs:275`, `VaultView.xaml.cs:419`). *One refuter argued the realistic PAN path is always a reference token, never a literal, and downgraded this. That is right for the vault's own flow and wrong for an agent that types a card number directly or scrapes an order confirmation.*

**`VaultItemInfo` now carries card PII while documenting itself as non-secret metadata (low, likely).** `VaultModels.cs:19-21` says "Never carries secret values", but `:35-39` add `CardholderName`, `CardExpiryMonth`, `CardExpiryYear` and `BillingAddress`, populated verbatim at `AeadVaultStore.cs:79-83`. This record is produced by `VaultResolver.cs:23` *before* the domain-binding (`:26`) and ACL (`:28`) checks run. Nothing leaks today because the only consumers are the operator UI and the resolver, but the contract is now false and the next consumer added on the strength of that comment leaks a cardholder name plus a full billing address.

### Card verdict

The vault store is the strongest new code in this commit range. The gates above it are the weakest. The gap between `docs/vault-design.md:78-84` and the implementation is the single most important documentation-versus-code divergence in the repo, because that section is what a judge or a user would read to decide whether storing a card here is safe.

## 4. Round-2 P0 Fix Verification

### P0-1: seal deletion. Verdict PARTIAL

**How it works.** `SettingsStore.Load` no longer branches only on `Tampered`. The old `else if (Tampered)` became a catch-all `else` (`SettingsStore.cs:93-117`) that computes `establishedSealWasRemoved = LastSealVerdict == Unsealed && (recovered is not null || SafeHasPriorSealEvidence())` (`:96-97`) and only then early-returns (`:99-100`). The durable evidence is an OS-event-log entry, `OsEventIds.SettingsSealEstablished = 1008` (`IOsEventLogSink.cs:46`), read at `App.xaml.cs:165-167` and written at `:168-177`.

**What is genuinely closed.** The exact round-2 exploit is dead, traced end to end. `ReadSeal` returns null (`:273`), `SettingsSeal.Verify` maps an empty seal to `Unsealed` (`SettingsSeal.cs:124`), the else branch runs `TryReadRecovery` (`:95`), the verdict is forced to `Tampered` (`:102`), the files are quarantined (`:288-293`), the recovered snapshot is restored and returned (`:106,:110`), and `App.xaml.cs:1063` fires the High notice. `del settings.json.seal` after editing the file now reverts and alarms. That is real.

**Where it fails.** The second half of the brief, "persist a durable bit outside settings.json so the no-seal path cannot be re-entered by deleting everything", does not exist for the shipping default. `WindowsEventLogSink`'s own comment says registering the source "needs admin ONCE" (`WindowsEventLogSink.cs:11,:26-43`), `installer/foreman.iss:24` is `PrivilegesRequired=lowest` and registers no source, and the only registrars are the opt-in elevated sidecar (`Foreman.EtwSidecar/Program.cs:145`) and the opt-in Guardian installer (`GuardianInstaller.cs:240`). On a stock install `_available` is false, `ReadOwnRecent` returns `[]` (`:76`), and `SafeHasPriorSealEvidence()` is permanently false. `establishedSealWasRemoved` degenerates to "the attacker forgot to delete `.lastgood`". The new test injects the witness (`SettingsStoreTests.cs:159` `SettingsStore.HasPriorSealEvidence = () => true;`), so it proves nothing about the default install, and there is no test with the witness absent.

Where the marker does exist it is unauthenticated and evictable. Measured on this box, `wevtutil gl Application` gives channelAccess `(A;;0x3;;;IU)`: Interactive Users hold read and write, `retention: false`, `maxSize: 20971520`. The project concedes this at `App.xaml.cs:1093-1094` and defends `LogChainAnchor` with a head-seal MAC, but event 1008 carries no MAC and no anti-flood, and `ReadOwnRecent` stops at a `rawScanCap = 20_000` raw-record scan (`WindowsEventLogSink.cs:85`). 20,000 raw Application records reach back ~50 days on this machine.

**Two sibling paths remain open, both critical:** deleting `settings.json` itself (never reaches the evidence check at all, `SettingsStore.cs:62`), and the rotation-adopt laundering path (`SettingsStore.cs:209`). Both are in section 5.

**First run and upgrade were checked for false reverts and found clean.** Genuine first run with no file returns defaults before any seal logic (`:62`). First run with an unsealed file, no recovery and no marker adopts (`:99-100`). Upgrade from a pre-`866af36` install with an intact seal verifies `Sealed` and records the marker (`:77-83`). I could not construct a legitimate-user silent revert on the main path.

### P0-2: guardian install root. Verdict INEFFECTIVE

**How it works.** `866af36` adds `GuardianInstallRoot` (HKLM64 `SOFTWARE\Foreman Agent Safety\InstallRoot`) and a pure decision `GuardianIntegrity.DecideForInstall` (`GuardianIntegrity.cs:66-94`): canonical layout (`:74-76`), recorded-root match (`:78-83`), publisher `Decide` if signed (`:85-86`), else require the explicit opt-in (`:88-89`), else require the subject also unsigned (`:90-91`), then trust (`:93`).

**What is genuinely fixed.** Four things, all real. The `client-policy.json` rollback the brief demanded is closed: `CaptureRaw` before the try (`GuardianInstaller.cs:78`), `RestoreRaw` in the catch (`:112`), HKLM restored at `:135`. The signed-release sibling is closed: swapping only `guardian\Foreman.Guardian.exe` under a signed install hits `Decide(referenceSigner != null, subjectSigner = null)` = false. `GuardianClientPolicy.VerifyClient` (`:74-80`) re-hashes at every pipe connection, so a post-install swap fails closed at runtime. A shipped unsigned build driven through the App fails closed (`GuardianControl.cs:32-36`).

**Why it does not close the hole.** Round 2 fixed the actor explicitly: "an attacker who stages their own unsigned layout and consents to their own UAC prompt" (`docs/audit-2026-07-22-round2-fix-verification.md:185`). Against that actor neither new control binds.

`GuardianIntegrity.cs:79` guards the root comparison with `!string.IsNullOrWhiteSpace(recordedInstallRoot)`, so a null anchor skips the check and falls through to the opt-in branch. The only writer is `GuardianInstaller.cs:93`, at the end of a successful elevated install; the shipping installer writes only an HKCU Run value (`installer/foreman.iss:57-61`). The Guardian is opt-in and off by default (`SetupHealth.cs:141-144`), so on essentially every real machine the value is absent. The round-2 chain replays verbatim: stage `%LOCALAPPDATA%\x\Foreman.exe` plus `x\guardian\Foreman.Guardian.exe`, run the fake Foreman for a live PID, then `runas x\guardian\Foreman.Guardian.exe --install --foreman-pid P --allow-unsigned-development`. Cost delta versus round 2: one extra argument. The success message at `:93` then claims the install "matched the recorded root" when no root was ever recorded.

`Program.cs:30` reads the flag straight from argv with no provenance check, and the attacker is the one invoking the binary. Even with an anchor recorded it pins a user-writable directory (`installer/foreman.iss:24,27`), so an in-place overwrite of `<root>\Foreman.exe` passes, and nothing remembers the previous install was `publisher_signed` (`GuardianClientPolicy.CreateForInstall` re-derives from disk, `:42-55`), so a signed install silently downgrades to a path+hash pin of the attacker's binary.

All three new tests pass `allowUnsignedDevelopment` as a caller-chosen literal, and `UnsignedInstall_MatchingRootStillRequiresExplicitDevelopmentOptIn` (`GuardianIntegrityTests.cs:50-54`) asserts `Trusted == true` for exactly the attacker's configuration. No test anywhere passes `recordedInstallRoot: null`, the state of every default machine.

*Dissent worth recording:* one refuter argued the chain is post-administrator (it starts with `runas` on an attacker binary) and therefore not an escalation. That is a fair severity argument. It does not change the verdict, because the anchor was added specifically to defeat this actor, the actor is documented as in scope, and the outcome (attacker binary persisted as the sole authorized SYSTEM pipe caller *and* the genuine Foreman permanently locked out) is strictly worse than what the same admin could do by hand.

### P0-3: event retention. Verdict REGRESSED

**How it works.** `EventRetentionPolicy.SelectVictims` (`EventRetentionPolicy.cs:17-24`) orders `Acknowledged` first, then `IsAgentReported` descending, then `Severity`, then `Timestamp`. `SelectAgentQuotaVictims` (`:27-33`) caps the agent partition. `BoundedEventHistory.Add` (`:28-37`) runs the quota trim then the capacity trim, protecting the arrival only when it is host and >= High (`:32-34`); `ForemanState.OnEvent` (`:115-131`) mirrors it with a 200-of-1000 agent quota.

**What holds.** The reported hole is closed on the named path. The agent partition is bounded in both stores. Provenance is not caller-supplied over MCP: every MCP publish site uses a `const` source. I could not find an agent-reachable path that mints a host-provenance event at >= High through the intended sources. All four consumer surfaces read the fixed stores.

**Where it fails.** The provenance term is `evt.Source.StartsWith("MCP.")` (`EventRetentionPolicy.cs:8-9`), and on the two highest-value host detection paths `Source` is built from the observed process's own filename: the decoy Critical uses `Path.GetFileName(d.Image)` (`App.xaml.cs:821`) and the WMI command detector uses `record.Name` (`WmiProcessWatcher.cs:242`, cred-sweep Critical at `:259`). A payload named `MCP.exe` produces host-detected Criticals that `IsAgentReported` classifies as agent-reported. Pre-fix ordering was `(Acknowledged, Severity, Timestamp)` with no provenance term, so this flips those records from last-evicted to **first**-evicted ahead of every host event including Info, and strips the arrival protection at `BoundedEventHistory.cs:32`. With the 1000-slot history at capacity the next published event evicts the decoy-read Critical; sustaining ~200 `report_suspicious_command` Criticals for ~17 minutes ages it out of `_alertById`, flipping `HasCritical` (`ForemanState.cs:72`) and `foreman_health` (`ForemanMcpTools.cs:32`) back to green. Same end state as the original P0-3 finding, reached more cheaply, through a mechanism this fix introduced.

A second sibling escapes the quota in the other direction: `ForemanMcpTools.cs:216-218` publishes `"Foreman.Ack"` on every successful `acknowledge_alert`, and `ForemanState.cs:138-143` returns true whenever the alert merely exists, so re-acking in a loop mints unbounded host-provenance events. `ForemanMcpTools.cs:1734` (`"Foreman.Vault"`) is a second such path.

The durable on-disk log was not touched at all. `EventLogStore.cs:159-161` still compacts by pure recency, `EventRetentionPolicy` appears nowhere in that file, and `ReportTaskStart` remains an unthrottled, ungated append primitive (`ForemanMcpTools.cs:487`, publish precedes every auth branch). See section 5.

### P0-4: supervisor wedge. Verdict REGRESSED

**Half of the fix is correct and sufficient.** `ElevatedSidecarController.cs:123-136` wraps `WaitForConnectionAsync` in a linked CTS with `CancelAfter(60s)`, publishes a High notice on expiry, and returns, so the `finally` at `:168-182` always runs, disposes the pipe server, and clears `_launchInProgress` (`:179`). The timer is armed only after `LaunchSidecar` returns, so a long UAC wait cannot trip it. That is a correct design and it closes P0-4 on its own.

**The supervisor half trades one permanent silent blackout for another.** Production wiring is tick = 30s (`App.xaml.cs:901`) with defaults 3/1/2 (`SidecarSupervisor.cs:49,57-59`), so relaunch #2 fires exactly 5 ticks, **150 seconds**, after the UAC prompt appears. The whole reason auto-relaunch exists is an unattended sidecar (`SidecarSupervisor.cs:10-16`), so the modal case is a consent prompt nobody answers for minutes. At 150s the supervisor calls `_relaunch()` = `_sidecar.Restart()` (`App.xaml.cs:845`) = `Stop(); Start()`. `Stop()` cancels run 1 while its thread is still blocked inside `Process.Start(UseShellExecute=true)` on the open prompt. `Start()` spawns run 2, whose `LaunchSidecar` hits the single-flight guard (`:237`) and returns false, and `:121` maps that refusal onto `_launchFailed = true`, the same flag that means "the operator declined UAC". `App.xaml.cs:891` feeds it to the supervisor as `launchDeclined`, and `SidecarSupervisor.cs:111` requires `!_launchDeclined()` to ever relaunch again. `_launchFailed` is cleared only by `Start()` (`:90`) or a handshake (`:157`), and the supervisor is the only automatic caller of `Start()`. Terminal state: no relaunch ever again, no notice ever again (the exhaustion notice at `:132-138` is inside the `!_launchDeclined()` branch and `_downNotified` was already set at `:117-120`), escape only via a manual Settings toggle the operator has no signal to perform.

It is worse than a no-op. When the operator finally clicks Yes, run 1 resumes with an already-cancelled `ct`, `WaitForConnectionAsync` throws immediately, the filter at `:129` is false so even the 60s High notice is skipped, and the pipe is disposed. The just-elevated helper starts, runs `DecoyAudit.Start()`, fails `pipe.Connect(5000)` (`Foreman.EtwSidecar/Program.cs:66-67`), returns 4 and exits. The operator granted administrator and got nothing, silently.

Direct answers to the review questions: (1) the bound is not correct in wall-clock terms; (2) it does not stack a second prompt while the first is on screen, but it destroys the pending launch and poisons the state; (3) `WaitForConnectionAsync` no longer lacks a timeout, that part is fixed; (4) the budget is still per-down-spell (`:79` zeroes `_relaunchAttempts` on any reconnect, a round-2 repeat); (5) the supervisor does not notify honestly in every terminal state.

The tests missed it because the rig's relaunch callback (`SidecarSupervisorTests.cs:22-26`) never sets `LaunchInProgress` or `LaunchDeclined`, and the rig overrides `maxLaunchInProgressTicks: 2` (`:32`) so the shipped value of 3 and the 30s wall clock are never exercised. `StuckLaunchInProgress_ExpiresAndRecoversInsteadOfWedgingSilently` passes on a path production cannot take.

**Recommendation is unusual for a P0: remove the supervisor-side bound.** With the controller's `CancelAfter` in place it is redundant for the bug it was added to fix, and the only remaining unbounded source is the untimed nonce read at `ElevatedSidecarController.cs:152`, which should get the same linked token.

### P0-5: rotation revert. Verdict PARTIAL

**How it works.** On `Tampered`, `Load` takes a new branch (`SettingsStore.cs:84-92`) into `TryAdoptAfterLocalSecretRotation` (`:194-218`), which requires: no guardian sealer (`:201`), a non-empty local secret (`:201`), `IntegritySecretRecentlyRegenerated() == true` (`:202`, wired to `McpAuthToken.RecentlyRegenerated` at `App.xaml.cs:164`), and `settings.json` byte-equal to `.lastgood` (`:210`). It then reseals and returns the original settings as `Sealed` with an explanatory fault (`:87-91`), surfaced as a Medium notice (`App.xaml.cs:1044-1046`).

**What holds.** The documented rotation is genuinely preserved. `mcp-setup.txt` tells the operator to delete `mcp.token` (`McpAuthToken.cs:263`); `LoadOrCreate` mints a fresh one during startup (`:73-93`, called at `App.xaml.cs:161`) before `SettingsStore.Load()` at `:182`, so the mtime is always "now" and condition (c) holds. Condition (d) holds in steady state because `.lastgood` is rewritten on every Save (`:152`) and every sealed Load (`:81`). The test `RecentLocalSecretRotation_PreservesAndResealsUnchangedSettings` (`SettingsStoreTests.cs:171-187`) exercises the real path. A non-rotation tamper is still caught. Disabling adoption entirely under the guardian sealer (`:201`) is the right call.

**Where it fails.** Three ways.

*The guard verifies nothing.* `:208-209` reads `settings.json.lastgood.seal` and checks only `Length != 0`. It never calls `Verify`. The entire proof that this is a rotation and not an attack is `currentJson == recoveryJson` between two files the attacker owns. See the critical in section 5. In the default local install this is not a capability increase (the seal key *is* the same-user-readable `mcp.token`, and `SettingsSeal.cs:27-34` documents that a same-user actor can recompute any seal), which is why one refuter dissented. It is nonetheless an unsound guard that becomes load-bearing the moment the local key is hardened, and the second test (`:189-204`) only covers the current-file-only edit.

*`RecentlyRegenerated` has no lower bound.* `McpAuthToken.cs:62` is `UtcNow - when < window`, true for any **future** mtime, so one `SetLastWriteTimeUtc(token, 2030)` arms the adoption path permanently, and clock skew or a restored backup does it accidentally.

*The same destruction still happens on a sibling trigger introduced by the same commit.* A `g1:` guardian-scheme seal plus prior seal evidence now produces a false `Tampered`, quarantine and defaults, in the strongest configuration, on a path `SettingsSeal.cs:117-121` explicitly documents as the graceful opt-out. That is a critical in section 5.

## 8. Refuted

Two findings did not survive adversarial refutation. They are recorded here so they are not re-raised in round 4.

**"The presence tap is cache-shared with the origin's password and touch-only, defeating the sole boundary on a card release" (proposed high).** The three code facts are true (`PresenceGate.cs:112-125` generic prompt, `:60` cache key includes only action and detail, `ResolveVaultCredential` absent from `ForcedUserVerification`). The premise that the tap is the *sole* boundary is false: `CuHeuristics.cs:33-38` returns a final Hold for any card-bearing action, so the operator must separately `cu_approve` that specific action, and `App.xaml.cs:366-368` routes that approval through `ApproveCuSensitiveAction` with `forcePresence: true` **and** `freshTap: true`, which bypasses the approval cache entirely (`PresenceGate.cs:59-74`) and is in `ForcedUserVerification` (`PresenceLock.cs:111`). A password tap for origin X therefore cannot silently cover a card release. The generic prompt string remains a real weakness and is kept as C9; the cache-sharing exploit is not real. *Caveat: this refutation depends on the card Hold actually firing, which H1 shows it does not for non-`type` verbs. Fixing H1 makes the refutation solid; leaving H1 open partially resurrects this.*

**"A held browser action, including every card fill, is approvable with the operator bearer token alone" (proposed high).** The structural facts are right: `ForemanMcpTools.cs:1763` and `App.xaml.cs:461` gate the presence tap on Desktop and Android only, and `CuBroker.cs:364` skips the delivery-time excursion re-gate for operator-approved items. But approval alone releases nothing. The action carries a reference, not a value, and plaintext leaves only via `cu_resolve_vault` to `ResolveVaultAsync` (`App.xaml.cs:516-554`), where both branches call `PresenceGuard.AuthorizeAsync(..., forcePresence: true)`, which bypasses the lock-off short-circuits and fails closed with no enrolled authenticator. The cache key embeds the live origin, capped at 300s. This is the documented intentional boundary (`ForemanMcpTools.cs:1683-1686`, `docs/vault-design.md:110`). One accurate residue: the justification comment at `ForemanMcpTools.cs:1760-1761` is imprecise, because `extension/background.js` `resolveTargetTab` lets an explicit `args.tabId` win over the pinned tab, so the extension confines only actions with no `tabId`. That is a doc-accuracy nit, kept as a low in section 6.

## 10. Assessment

### Trajectory across three rounds

Round 1 found 4 criticals in a codebase nobody had audited. Round 2 verified the fixes and found that each critical was closed on the exact path the audit named while a sibling stayed open, plus 9 regressions. Round 3 finds the same shape again, in every one of the five P0 remediations, plus two new destructive regressions the fixes themselves introduced.

That pattern is worth naming plainly, because it is the single most important thing in this report and it is a process problem, not a competence problem. The individual fixes are well written. `866af36`'s install rollback, the `CancelAfter` on the sidecar connect wait, the structural move of seal verification inside `Load()`, the two-tier agent quota, all of these are correct code that does what it says. What is missing is the step where the fix author asks "what is the sibling of the path the audit named", and the step where the regression test is written against the bypass rather than the report. Every green test added in `866af36` passes on a path the exploit does not need to take. `RecentlyLocalSecretRotation_DoesNotBlessCurrentOnlyEdit` edits one file when the attack edits two. `UnsignedInstall_MatchingRootStillRequiresExplicitDevelopmentOptIn` passes a root when the attack has none. `FastPath_PaymentCardReference_HoldsAndIsFinal_EvenInTextField` uses verb `type` when the attack uses `click`. `StuckLaunchInProgress_ExpiresAndRecoversInsteadOfWedgingSilently` passes on a path production cannot take. `SettingsStoreTests.cs:159` injects the witness that does not exist on a real install. Five for five.

The fix that makes this concrete: writing the test *first*, from the failure scenario in the report, before touching the code. If that test cannot be written because the scenario is not reproducible, the finding needs re-litigating before the fix ships.

### What is genuinely strong, with credit

This deserves to be said clearly, because there is a lot of it and it is not the norm.

**`AdbBridge` is the best code in the repo.** Every adb invocation is a fixed argument vector with validated ints and a keycode map; the on-device `input text` charset excludes every shell metacharacter (`AdbBridge.cs:462-473`); the binary is pinned and launched via its `GetFinalPathNameByHandle`-resolved path, which closes the junction TOCTOU round 1 found; `ADB_SERVER_SOCKET` and `ANDROID_SERIAL` are scrubbed. There is no finding against it in this audit that is not really a finding against the broker above it.

**The Desktop CU path is properly defended.** Verb allowlist (`CuBroker.cs:106-113`), one-window confinement re-gated at delivery with no `OperatorApproved` escape (`:326-347`), HUD-visible-or-withhold (`CuExecutorPump.cs:43-56`), presence-minted bind tokens. The panic epoch CAS in `SubmitAsync` (`:243-255`) correctly refuses to resurrect an item a halt already rejected. That is the kind of detail that only appears when someone thought about the race.

**The event log's crash handling is unusually careful.** `RepairUncommittedTail` (`EventLogStore.cs:525-550`) repairs only a torn tail and fails closed on middle damage. `SeedState` advances in-memory state only after the append lands (`:136-145`). `RotateAndReseal` resets chain state on any mid-rotate failure (`:245-255`). `Rewrite` now swaps atomically via tmp plus `File.Replace` (`:578-584`), closing the round-2 atomicity gap. `LogAnchor.SealPayloadHead` (`LogAnchor.cs:71`) domain-separates the anchor MAC from the `.head` seal, which closes a subtle seal-lifting forgery nobody asked for.

**The vault's crypto is right.** Fresh salt and nonce per write, double-bound header AAD, Argon2id at 64 MiB / 3 passes, validation duplicated in the store rather than trusted from the UI, per-deposit ephemeral keys with SPKI-hash AAD, and sealed-versus-clear pubkey swap detection. The card addition did not weaken a single one of these, and the entry-ID design that keeps a card unreachable by a legacy two-segment reference is a genuinely thoughtful piece of backward-compatibility security.

**The MCP scoping pass is mostly complete and mostly correct.** About 30 of 43 tools pin harnessId, processId and profileName to the token identity rather than the parameter. `CanMutate` fails closed on peer-mismatch for the mutating tools. `McpAuthToken`'s stateless MAC design means a harness identity cannot be forged without the install secret. Secret redaction is applied at every egress including the durable log. The four that are wrong are wrong in the same way (one control applied to the tool the audit named, not its sibling), which is a fixable pattern rather than an architectural problem.

**The detection engine's plumbing is solid.** The two-pass prune grace so WMI's delete event reliably wins the orphan-accounting race (`ProcessTreeTracker.cs:97-144`), the self-healing watcher watchdog with degrade and recover notices (`WmiProcessWatcher.cs:64-146`), the ancestor walk stopping at OS hosts, matching both raw and normalized text so normalization can only add detections (`CommandAnalyzer.cs:44-54`), the cred-013 downgrade refused when the line also credential-filters the env output (`:26-29`), `AgentConfigScanner`'s fail-closed reparse handling and honest `ScanIncomplete` signal, `KillProcess`'s start-time identity pin.

**The tray and dashboard are hardened well beyond what a tray app usually gets.** Single-flight refresh coalescing (`TrayController.cs:313-323`), never swapping an open `ContextMenu` (`:484`), every `Shell_NotifyIcon` call wrapped and `CrashLog`'d with a `ForceCreate` recovery timer, and `DashboardWindow` unsubscribing from the bus and disposing every hosted view on close (`DashboardWindow.xaml.cs:967-975`) so repeated open/close cycles leak nothing.

**The CI supply chain is better than most production repos.** Every action SHA-pinned with a documented rationale and Dependabot maintenance, no `pull_request_target`, no secrets in CI so fork PRs cannot reach release credentials, version and user inputs passed through `env:` rather than interpolated into `run:` blocks, and a correct signing order (inner binaries first, installer last, checksums over signed bytes, attestation after signing). The gaps found are at the edges of an otherwise correct design.

And a specific point of intellectual honesty worth crediting: `SettingsSeal.cs:26-34`'s doc comment was corrected in `866af36` to drop the false SACL and anchor claims it previously made. That is someone choosing to make the documentation less impressive because it was wrong. It is the opposite of the pattern this report keeps flagging elsewhere, and it should be the model.

### The single most important thing to fix

Not the exploit with the biggest number. The one where the code claims a protection it does not deliver, because that is the class of defect this codebase keeps producing and the class that hurts a security product most.

**Make the decoy tripwire's arm state observable, and make deleting a decoy an alert (C7, P0-5).**

The reasoning: the honeytoken tripwire is the product's most differentiated feature, it is what "smart AV for AI agents" means concretely, and today an attacker disarms it permanently with `File.Delete` on six files they own, generating no record, after which the Setup Health screen tells the operator twice that it is armed and working. `Foreman.EtwSidecar/Program.cs:61` throwing away `Start()`'s return value is a one-line bug with a total-detection-loss consequence, and `SetupHealth.cs:128` keying a green row on pipe connectivity rather than armed-path count is the exact false-green the calibration brief warns about. Fixing it costs a widened ACE (`DecoyAudit.cs:163`), a widened query (`:83`), a new pipe frame carrying armed counts, and a health row that reads it. Small, self-contained, no architectural risk.

Everything else in P0 is a hole an attacker has to work to reach. This one is a hole that closes itself while telling the operator it is fine.
